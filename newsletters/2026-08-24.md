### NVIDIA Turned a 30% Model Into a 100% Agent. Here's How to Build the Same Harness in Java

NVIDIA's research team just published results that reframe how we think about AI capability. On the ARC-AGI-3 benchmark, Claude Opus 5 alone scored 30.2%. Wrapped in NVIDIA's agent system called AVO, the exact same model hit 100%—all 183 levels solved, using 12% fewer actions than the previous best. No retraining. No bigger model. Just better system design.

This crystallizes a new discipline: harness engineering. The harness is everything around the model—how it receives context, uses tools, maintains state, responds to feedback, recovers from failure, and sustains progress over long tasks. NVIDIA's architecture breaks down into four components: memory (what survives between steps), tools (what actions are possible), feedback (what grounds progress), and recovery (what allows work to continue beyond a single invocation).

The article walks through building AVO's architecture in plain Java 21. You get four classes: a Tool contract with structured input/output, AgentState for scratch memory, AgentLoop as the supervisor that validates results and recovers from failure, and at least one real tool implementation. The harness is a loop with guardrails, not a framework—you don't need LangChain or Spring AI for the core, just Jackson and deliberate design.

Why it matters: The gap between a bad harness and a good one is now measurable in tens of percentage points—more than most model upgrades deliver. In GPU kernel optimization, AVO autonomously explored 500+ directions and produced kernels up to 10.5% faster than FlashAttention-4. That's a system letting a model be slightly clever hundreds of times without breaking. For Java teams running AI-powered backends, this is the blueprint for making agents production-ready.

### Kodebits Day 80: Safe Call Operator

Here's today's Kotlin challenge from Kodeco's daily series: What does this print?

```kotlin
fun main() {
    val s: String? = "code"
    val len = s?.length
    println(len)
}
```

The answer is 4. The safe call operator (`?.`) returns the property value if the receiver is not null, otherwise it returns null. Since `s` contains the string "code", `s?.length` evaluates to 4 and that's what gets printed.

This tiny operator is one of Kotlin's most elegant null-safety features. In Java, you'd need an explicit null check or risk a NullPointerException. Kotlin bakes the check directly into the access syntax. If `s` were null, `len` would be null too—no crash, no ceremony, just propagated nullability.

The safe call operator chains beautifully: `person?.address?.street?.name` returns null if any step in the chain is null, avoiding the nested if-statements that plague Java codebases. Combined with the Elvis operator (`?:`), you get concise fallback logic: `val length = s?.length ?: 0` gives you zero when `s` is null.

Why it matters: Null-safety isn't just about preventing crashes—it's about making your intent explicit in the type system. When a variable is `String?`, the compiler forces you to handle the null case. The safe call operator is the most common way to do that without ceremony. If you're still writing Java-style null checks in Kotlin, you're missing one of the language's core design wins. This challenge is small, but it's the foundation for writing Kotlin that's both safe and readable.

### More than just code review

Simon Willison drops a sharp observation about working with coding agents: the key skill isn't reviewing every line of code they write. It's confidently instructing them on what to change and confidently verifying those changes were applied correctly. Sometimes that means reading every line. Often it doesn't.

This cuts against the instinct many developers have when AI writes code: to treat it like a junior engineer's pull request and scrutinize every character. But as Willison points out, eyeballing every line has never been the most effective way to validate a software change—even when humans write it. We use tests, we check behavior, we validate interfaces, we monitor runtime characteristics.

The same principles apply to agent-generated code. If you've specified the change well and the agent has good tooling (tests, linters, type checkers), you can verify correctness at a higher level. Did the tests pass? Does the API contract match? Does the output behavior align with the spec? You're not absolving yourself of responsibility—you're using the same validation techniques you'd use for any code change.

Why it matters: As coding agents become more capable, the bottleneck shifts from "can the agent write this" to "can I effectively direct and validate it." Teams that figure out how to verify agent work without line-by-line audits will move faster. Teams that don't will drown in review overhead or—worse—skip validation entirely and ship broken code. The skill here isn't code review. It's systems thinking about verification.

*Source: [Simon Willison](https://simonwillison.net/2026/Aug/22/more-than-just-code-review/)*

### Signatures, be true: domain errors and functional handling in Kotlin

JetBrains tackles a silent killer in Kotlin codebases: functions that return Unit but can fail in multiple ways. When a signature says "this completes without returning a value," it hides every possible error—invalid input, closed signing windows, database failures. The post advocates encoding errors in return types using sealed classes or Result types, making failure modes explicit and forcing callers to handle them. This functional approach turns runtime surprises into compile-time contracts, eliminating a whole class of bugs that occur when developers assume success.

*[JetBrains Kotlin](https://blog.jetbrains.com/kotlin/2026/08/signatures-be-true-domain-errors-and-functional-handling-in-kotlin/)*

### What Spring Data Tests Can Miss: Testing Beyond Hibernate's Persistence Context

Here's a testing trap that catches even experienced Spring developers: calling a repository's `findById` in a test after the entity is already managed gives you the cached object, not a fresh database fetch. Hibernate's first-level cache returns the in-memory version without querying the database at all. Your test passes, but you've validated nothing about persistence. The solution is clearing the EntityManager or using a separate transaction. This matters because production code rarely has entities pre-loaded in the same context, so your tests are validating a scenario that never occurs in real usage.

*[Dev.to Java](https://dev.to/kamenivanov/what-spring-data-tests-can-miss-testing-beyond-hibernates-persistence-context-chapter-7-5d7k)*

### I Found a P0 Auth Bypass by Testing What null Does to BCrypt

A developer found a critical auth bypass while boundary-testing a Spring Boot supply chain platform: `BCrypt.matches(null, hash)` was returning true. Any account with a null password field—soft-deleted users, malformed requests, anything leaving password unset—could authenticate with any typed password. The issue wasn't BCrypt itself, but how the application handled null inputs before reaching the hash comparison. It's a reminder that security boundaries need explicit null handling, and that "this shouldn't be null" assumptions are where vulnerabilities hide.

*[Dev.to Java](https://dev.to/kumar_swamy_0b18518741d91/i-found-a-p0-auth-bypass-by-testing-what-null-does-to-bcrypt-ffc)*
