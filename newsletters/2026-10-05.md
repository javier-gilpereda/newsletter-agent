### How Java HashMap Prevents Hash Collision DoS Attacks

In 2011, security researchers demonstrated a devastating attack: a tiny 2MB payload could freeze a CPU core for 45 minutes by exploiting hash collisions in HashMap. The vulnerability was elegant and brutal—by crafting strings that generated identical hash codes, attackers could force thousands of entries into a single HashMap bucket, turning O(1) lookups into O(N) nightmares.

The attack worked because Java's String.hashCode() is deterministic and publicly documented. Strings like "Aa" and "BB" produce the exact same hash code (2112), and once you understand the algorithm, you can generate thousands of colliding keys. When a web server processes a malicious form with these colliding field names, the HashMap degrades catastrophically, performing up to 500,000 comparison operations for just 1,000 keys.

Java 8 introduced a clever defense: the treeify threshold. When a bucket's linked list grows beyond 8 elements and the map contains at least 64 buckets total, the JVM automatically converts that bucket into a Red-Black tree. This drops search complexity from O(N) to O(log N)—for 1,000 colliding keys, that means roughly 10 comparisons instead of 1,000. The threshold of 8 is carefully chosen; under normal circumstances with good hash distribution, the probability of any bucket naturally reaching 8 elements is only 6 in 100 million. This ensures the tree conversion overhead only kicks in during anomalies or attacks, making the defense both effective and efficient.

### Spring AI Modular RAG and TypeSafe Jev: Retrieve More, Keep Only What Answers

Naive RAG implementations suffer from three critical flaws: users don't write optimized search queries, vector similarity doesn't guarantee usefulness, and retrieved text is untrusted input that can hijack your prompts. Spring AI's new modular RAG architecture addresses all three with pluggable components that transform a simple QuestionAnswerAdvisor into a sophisticated pipeline.

The RetrievalAugmentationAdvisor breaks RAG into distinct phases: pre-retrieval transforms queries with RewriteQueryTransformer and expands them with MultiQueryExpander, retrieval branches run in parallel per query, and post-retrieval filters and reranks results before generation. Each phase implements a small, swappable interface. The demo showcases TypeSafe's Jev model as a post-processor—it judges every retrieved chunk in milliseconds, returning calibrated scores that filter noise and rerank by relevance.

Here's the practical impact: when asked "Did Hurricane Milton make landfall in Florida?", the naive approach embeds that verbose question directly, dragging conversational noise into vector search. The modular pipeline first rewrites it into crisp search queries, retrieves chunks in parallel, then uses Jev to filter out references that merely mention Milton without answering the question. The result: fewer tokens to the LLM, faster responses, and answers grounded in actually relevant context. The complete example lives in the spring-ai-rag module, requiring just the RAG dependency and TypeSafe starter to get started.

*Source: [Spring Blog](https://spring.io/blog/2026/10/02/spring-ai-modular-rag-typesafe-jev)*

### Embabel vs LangGraph4j: Two Agentic Philosophies for Investment and Risk Analysis in BFSI

Two frameworks offer radically different approaches to building multi-step AI agents in Java. Embabel takes a goal-oriented approach: you provide typed actions and let an AI planner autonomously decide execution order. LangGraph4j requires explicit graph construction, with developers manually defining nodes, edges, and flow control. The article demonstrates both philosophies through a real-world BFSI scenario involving investment and risk analysis. For Java shops building agentic systems, the choice comes down to control versus autonomy—whether you want to choreograph every step or trust the framework to reason about task sequencing. Both keep you in the JVM without sacrificing AI capabilities.
