### Building AI Agents with Spring AI — Tool Calling, Memory, and Autonomous Workflows

Large language models can generate impressive text, but they can't actually do anything in your application—until you give them tools. That's the core insight behind AI agents, and Spring AI now makes building them straightforward.

The difference is fundamental. A traditional LLM application takes a prompt and returns text. An agent-based application lets the LLM decide what actions to take, execute those actions through your application's APIs, observe results, and continue reasoning until it accomplishes the goal. When a user asks "What's the status of my order?" an agent doesn't just explain order tracking—it calls your order service, retrieves live data, and answers with real information.

Tool calling is the mechanism that makes this possible. You expose functions like getOrderStatus(), cancelOrder(), or createSupportTicket() to the model. When the LLM determines it needs data or should perform an action, it requests the appropriate tool. Your application executes the function against your actual systems—databases, REST APIs, payment processors, CRMs—and returns the result. The LLM then incorporates that result into its reasoning.

This architectural shift transforms LLMs from text generators into interfaces for your entire application ecosystem. A sales assistant can get customer data, create leads, and schedule meetings. A support agent can search your knowledge base, access accounts, and create tickets. An internal developer assistant can search documentation, check build status, and file issues.

The article distinguishes this from RAG (Retrieval-Augmented Generation), which primarily retrieves static information. Tool calling is about live data and actions—the difference between reading documentation about orders versus actually checking order status in your database. For enterprise Java developers working with Spring Boot, Spring AI provides the framework to build these agent architectures with familiar patterns, making AI applications genuinely useful rather than merely conversational.

### GPT-4o vs Claude 3.5 Sonnet vs Gemini 2.0: Which AI Model Should Developers Choose in 2026?

The AI landscape for developers in 2026 is dominated by three flagship models: OpenAI's GPT-4o, Anthropic's Claude 3.5 Sonnet, and Google's Gemini 2.0. Each promises faster code generation, smarter debugging, and deeper IDE integration—but they differ significantly in ways that matter for real projects.

Performance trade-offs are nuanced. Latency varies depending on whether you're generating a quick code snippet or processing a 100K-token codebase context. Token limits affect whether you can feed an entire microservice into the model for refactoring suggestions. Context handling determines how well the model maintains coherence across multi-file changes.

Cost efficiency becomes critical at scale. Pay-per-token pricing versus subscription models impact your budget differently depending on usage patterns. If you're running automated code reviews in CI/CD pipelines or generating documentation for every pull request, those per-token costs add up fast. Understanding the pricing structure for your specific workload—batch processing versus interactive sessions—makes a significant difference.

Tooling and ecosystem support varies considerably. Native SDKs for Java and Kotlin, IDE plugins for IntelliJ IDEA, integration with Spring Boot applications, and support for your specific tech stack all factor into developer productivity. One model might excel at general code generation but lack robust tooling for your language. Another might have excellent Claude Code integration but cost more for high-volume use.

The comparison highlights that there's no universal winner. GPT-4o might excel in certain coding tasks, Claude 3.5 Sonnet in others, and Gemini 2.0 in different scenarios. The best choice depends on your specific needs: latency requirements, budget constraints, preferred programming languages, and how the model fits into your existing development workflow.

### Why I Don't Want an LLM Generating Java Business Logic

A pull request arrives. A few hundred lines of Java implementing a new discount rule: tiered thresholds, regional exceptions, something about loyalty tiers that nobody can quite explain. It compiles. The tests pass. An LLM wrote it in about forty seconds. Now the hard question: who reviews it?

This scenario captures a growing tension in software development. LLMs have become remarkably capable at generating syntactically correct code that passes basic tests. For boilerplate,DTO mappings, or standard CRUD operations, they're genuinely useful. But business logic sits in a different category—it encodes domain knowledge, edge cases, regulatory requirements, and the accumulated wisdom of how your specific business actually works.

The concern isn't that LLM-generated code is always wrong. It's that determining whether it's right requires the same deep understanding you'd need to write it yourself. When an LLM generates a discount calculation, how do you verify it handles leap-year edge cases correctly? That it respects regional tax regulations? That it won't break when the business adds a new customer tier next quarter? The review burden doesn't disappear; it shifts.

There's also the maintenance question. Six months later, when the business rule changes, developers need to understand the existing logic to modify it safely. LLM-generated code often lacks the structure and clarity that comes from human reasoning about a domain. It might work, but it doesn't necessarily communicate intent.

The article argues for thoughtful boundaries. LLMs as coding assistants for well-understood patterns? Valuable. LLMs generating the core logic that defines your business value? Risky. The speed gain in writing code gets offset by increased review time, reduced maintainability, and the subtle erosion of team understanding about how your system actually works. Sometimes the slowest way is the fastest way.

### Spring Boot 4.1 Made gRPC a First-Class Citizen: When to Use It vs REST

Spring Boot 4.1 elevated gRPC to first-class status, addressing common integration pain points that REST developers face. The author reflects on an order-processing system where REST integrations suffered from three recurring problems: payload size causing serialization bottlenecks, client-server contract drift due to optional API documentation, and hand-rolled server-side streaming implementations. gRPC solves these with efficient binary serialization, strongly-typed contracts enforced by Protocol Buffers, and native bidirectional streaming. However, REST still wins in scenarios requiring broad client compatibility, human-readable debugging, or simple public APIs. The article provides practical guidance on choosing between the two based on your specific use case.
