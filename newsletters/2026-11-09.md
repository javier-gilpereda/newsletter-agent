## In Depth

### Claude Code is accidentally exposing secrets all over GitHub

If you're using Claude Code, you need to hear this: security researchers at Apiiro have discovered thousands of exposed secrets—database passwords, API tokens, root logins—sitting in public GitHub repositories. The culprit? Claude Code's settings files.

Here's what's happening: when you approve a shell command in Claude Code and select "Yes, and don't ask again," that approval gets stored in a local `.claude/settings.local.json` file. The problem is that the command itself—including any embedded secrets—often gets written verbatim to this file. While Anthropic adds this file to your global `.gitignore`, that protection doesn't carry over at the repository level. If you clone a repo to another machine or convert a folder into a repo later, that sensitive file can accidentally get committed and pushed to GitHub.

Apiiro found over 100,000 instances of these settings files on public GitHub, with roughly 1,100 containing actual secrets from 63 different organizations. Even worse, Claude Code sometimes commits changes to these settings files automatically, without explicit user action. And once those secrets hit GitHub, they persist in forks even after you remove them from the original repo.

Why it matters: This was first flagged in bug reports back in August 2025, but those reports were closed after 60 days of inactivity. Claude Code's Boris Cherny has since acknowledged the issue on Hacker News, recommending users switch to "auto mode" and use secret scanners. The team is exploring built-in secret scanning for the future. But here's the catch—Apiiro found that 215 of the leaked secrets weren't even detected by popular scanners like gitleaks and TruffleHog.

If you're a Claude Code user, audit your repositories now. Check for `.claude/settings.local.json` files in your public repos, rotate any exposed credentials, and consider switching to auto mode while the team works on a proper fix. This is a reminder that AI coding assistants, while powerful, introduce new security surfaces we're still learning to protect.

*Source: [Ars Technica](https://arstechnica.com/ai/2026/11/claude-code-settings-files-expose-thousands-of-secrets-on-github/)*

### Spring AI for beginners: build your first AI app in Java

Spring AI brings the familiar Spring Boot development experience to AI engineering, letting you integrate language models with the same dependency-injected, fluent API style you already use. Think of it as Spring's answer to Python's LangChain—it's not a model itself, but rather the integration layer connecting your Java applications to whatever LLM you choose.

The core of the beginner experience is the `ChatClient`, which follows the same fluent pattern as Spring's `WebClient` and `RestClient`. Spring Boot auto-configures a `ChatClient.Builder` for you. Inject it, build the client, and you're ready to make model calls. A complete working endpoint is remarkably simple: inject the builder, create a client, and chain `prompt()`, `call()`, and `content()` to get a response. The same code works whether you're talking to OpenAI, Anthropic, or a local model—the abstraction handles the differences.

Getting started requires the Spring AI BOM, a provider starter (like `spring-ai-starter-model-openai`), and basic configuration. The framework handles auto-configuration, giving you a ready-to-use `ChatClient.Builder` out of the box. From there, Spring AI provides rich building blocks: system prompts for controlling model behavior, advisors for cross-cutting concerns like logging and rate limiting, vector stores and embeddings for retrieval-augmented generation (RAG), tool calling for connecting models to external APIs, structured output for type-safe responses, and even Model Context Protocol (MCP) support for standardized tool integration.

Why it matters: Spring AI makes AI integration accessible to Java developers without requiring a Python context switch or wrestling with low-level model APIs. If you're building Spring Boot applications and want to add AI capabilities—whether that's chatbots, content generation, or semantic search—Spring AI gives you a production-ready path forward. The framework is actively evolving, with Spring AI 2.1.0-RC2 recently adding typed decision APIs and tool call delta streaming, showing that the ecosystem is maturing quickly.

*Source: [Dev.to Java](https://dev.to/protsenko/spring-ai-for-beginners-build-your-first-ai-app-in-java-4amn)*

### Agentic AI Architecture: Current Challenges and Future Opportunities

We're entering a new era of software architecture. While microservices and cloud-native systems have dominated for years, agentic AI architecture is emerging as the next major paradigm—one that will require architects and engineers to fundamentally rethink how systems are designed, built, and operated.

Traditional systems are deterministic: you can reason about them, scope functionality, test changes, and predict behavior even during failures. They process data using logic defined in code or retrieved from databases. Agentic AI architectures are different. They shift from operating on raw data to working with knowledge, elevating IT's role from data management to knowledge-level support for business operations. Instead of humans applying business rules and judgment atop systems, AI-enabled capabilities bring that intelligence directly into the software itself.

This transition brings substantial complexity. Agentic AI architecture layers atop existing microservices and cloud-native patterns, forcing teams to master new concepts, techniques, and technologies. Many well-established practices—testing strategies, observability patterns, security models—require rethinking or substantial adaptation. The architecture is still in its infancy, demanding significant investment from organizations ready to adopt it. And it won't replace existing architectures overnight; instead, it will coexist with today's systems for quite some time until they eventually morph into a unified paradigm.

Why it matters: The industry is moving fast. GitLab 19.5 has already positioned agentic development as a core platform feature. Grab has published case studies on safely handling the surge in AI-generated code changes. New tools like Entire's Git forge are being designed specifically for human-agent collaboration. If you're an architect or senior engineer, now is the time to start learning. The shift to agentic AI architecture won't happen all at once, but the foundation is being laid today. Understanding the challenges—non-determinism, governance, testing, observability—and the opportunities—knowledge-level automation, productivity gains, new capabilities—will position you to lead rather than follow as this new paradigm takes hold.

The tools.jar file was bundled with older JDK versions but removed in JDK 9+. If your Maven project has it defined as a system dependency, you'll hit build errors. ### Java's AI Path Has Two Tracks: FFM Today, Babylon Tomorrow

Java's approach to AI inference doesn't stop at calling remote services. A recent Devoxx Belgium session by Ana-Maria Mihalceanu outlined two platform-level paths: using the Foreign Function and Memory (FFM) API to connect Java to native inference runtimes today, or using Project Babylon's code reflection to express model logic in Java and translate it for execution on specialized hardware. The FFM approach works now, giving Java applications direct access to performance-critical native libraries, while Babylon represents a longer-term vision for platform-native AI integration.

*[Dev.to Java](https://dev.to/jamilxt/javas-ai-path-has-two-tracks-ffm-today-babylon-tomorrow-hkf)*
