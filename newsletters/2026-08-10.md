## In Depth

### Auto mode is now the default in Claude Code

Starting August 14, Claude Code made auto mode the default for Pro, Max, and Team plans—a shift backed by months of safety testing and real-world data. The move addresses a surprising finding: developers approve 97% of permission prompts, suggesting habitual clicking rather than careful review. In contrast, when Claude presents execution plans for approval, users reject 39% of them, indicating they engage more thoughtfully with higher-level decisions than individual command approvals.

Auto mode routes tool calls through a classifier designed to block irreversible, destructive, or external actions—without interrupting your flow with constant prompts. If Claude hits three blocks in a row or twenty in a session, it falls back to manual approvals. Anthropic's testing—including red-teaming, prompt-injection evaluations, and a study with over 1,000 testers—showed auto mode matched or beat manual review on every safety measure. The company is also dropping charges for the classifier's token overhead.

The productivity gains are real: Teams and Enterprise users running auto mode ship roughly 25% more pull requests. By letting Claude work autonomously for longer stretches, developers using models like Claude Opus 5 can leave tasks running for hours without babysitting. Companies like Adobe, Nuro, and Gusto have already made auto mode their production standard. Enterprise admins still have time to review the change, and any user can opt back to manual mode through settings. This isn't just a UX tweak—it's a fundamental bet that smart guardrails beat reflexive clicking.

*Source: [Claude Blog](https://claude.com/blog/auto-mode-default-in-claude-code)*

### Stop Letting Claude Code Hallucinate Your Modernization: Write OpenRewrite LST Recipes Instead

Letting AI agents directly rewrite massive Java codebases is risky business—hallucinated API calls and broken imports can slip through unnoticed. The smarter approach? Use Claude Code to generate deterministic OpenRewrite recipes, then let type-safe tooling execute the actual transformations. This article makes a compelling case for separating LLM logic generation from code transformation.

OpenRewrite works with Lossless Semantic Trees (LST)—type-attributed AST structures that preserve full semantic information, not naive text manipulation. Instead of prompting Claude to edit hundreds of files directly, you prompt it to write a JavaVisitor-based recipe targeting specific patterns (like Spring Boot 3 migrations or JDK 26 virtual thread upgrades). The example recipe shown uses MethodMatcher to identify Executors.newFixedThreadPool calls and replaces them with newVirtualThreadPerTaskExecutor via JavaTemplate—all backed by the Java compiler's type system.

Once you've generated and unit-tested the recipe with Claude's help, you execute it deterministically via rewrite-maven-plugin in a clean CI container. This gives you 100% reproducible diffs across your entire codebase with zero semantic drift. The LLM handles the creative, logic-heavy work of writing the recipe; the AST engine handles the precise, deterministic transformation. This pattern isolates non-determinism to the recipe authoring phase while keeping your production target repo completely deterministic. If your AI-driven refactor isn't backed by a proper semantic tree parser, it doesn't belong near production code.

*Source: [Dev.to Java](https://dev.to/machinecodingmaster/stop-letting-claude-code-hallucinate-your-modernization-write-openrewrite-lst-recipes-instead-il6)*
