### Introducing the Kotlin Benchmark for AI Coding Agents

JetBrains just released the Kotlin Benchmark, an official evaluation framework designed to measure how well AI coding agents handle real-world Kotlin engineering tasks. This isn't about testing a model's grasp of syntax—that's what Kotlin_HumanEval already covers. Instead, this benchmark looks at repository-level work: reading an issue, navigating an existing codebase, and producing a patch that actually passes tests.

Built on the SWE-bench methodology, the first public iteration includes 105 tasks pulled from active open-source Kotlin projects. Each task is validated in a containerized environment, and solutions only count as resolved if they pass the required verification. It's strict, deliberate, and closer to what developers face day-to-day than simple coding challenges.

Early results are impressive. Claude Code with Opus 4.7 xhigh topped the leaderboard at 85.71% resolution (90 of 105 tasks), followed closely by JetBrains Junie and Codex configurations at around 81.9%. Keep in mind these scores reflect the first iteration and don't yet include the very latest model releases—updates are coming.

Why does this matter? For teams evaluating AI coding assistants, vendor claims only tell you so much. The Kotlin Benchmark offers a shared reference point grounded in real tasks, though your mileage will vary depending on your architecture, internal APIs, and code standards. JetBrains is treating this as a continuous pipeline, not a one-and-done test. They plan to expand coverage to Android and Kotlin Multiplatform, add metrics beyond correctness (like cost and maintainability), and evaluate more agents and configurations. The benchmark assets and datasets are open-source and available on GitHub, so you can run your own evaluations or contribute improvements. If you're working with Kotlin and AI tooling, this is a credible way to cut through the hype.

*Source: [JetBrains Kotlin](https://blog.jetbrains.com/kotlin/2026/07/introducing-the-kotlin-benchmark-evaluate-ai-coding-agents-on-real-world-kotlin-tasks/)*

### Claude Code sends 33k tokens before reading the prompt; OpenCode sends 7k

A detailed performance teardown from Systima AI reveals that Claude Code carries significantly more token overhead than competitors—and the gap is larger than you might expect. When asked for a simple one-line reply, Claude Code consumed roughly 33,000 tokens in system prompts, tool schemas, and scaffolding before the user's prompt even arrived. OpenCode, running the same model and tasks, used about 7,000.

That's just the baseline. Cache efficiency tells a more nuanced story. OpenCode's request prefix stayed byte-identical across runs, meaning it could cache the payload once per session and retrieve it cheaply. Claude Code, by contrast, rewrote tens of thousands of prompt-cache tokens mid-session on the same task—sometimes writing up to 54 times more cache tokens than OpenCode. Since cache writes are billed at a premium, that explains why usage dashboards climbed faster with Claude Code.

In production setups, the overhead compounds. A 72KB instruction file (like AGENTS.md) adds another 20,000 tokens on average to every request. Five modest MCP servers tack on 5,000 to 7,000 more. By the time a real-world configuration sends its first request, you're 75,000 to 85,000 tokens deep before typing a word. Subagents make it worse: a small task that cost 121,000 tokens done directly ballooned to 513,000 tokens when delegated to two subagents, because each one bootstraps independently and the parent consumes the full transcript.

There's one scenario where Claude Code came out ahead: on a multi-step task, it batched tool calls into fewer requests, resulting in a lower total than OpenCode's turn-by-turn approach. But when the researchers re-ran the same task on a newer model, Claude Code's cost nearly doubled to around 298,000 tokens versus OpenCode's 133,000. Every token of harness payload is context you can't spend on your actual task. If you're running agentic AI in production—especially under frameworks like the EU AI Act that expect you to log and understand system behavior—knowing what your agent actually sends isn't optional anymore.

*Source: [Systima AI](https://systima.ai/blog/claude-code-vs-opencode-token-overhead)*

### LLM Tool Call Reasoning Using Embabel Agentic AI Framework

Baeldung just published a practical guide on using the Embabel Agent Framework in Java to gain observability into how AI agents reason about tool-call selection. If you've been building or experimenting with agentic systems in Java, this is worth a look—it tackles a real pain point that often gets glossed over in vendor demos.

The challenge with many AI agent frameworks is that tool selection happens inside a black box. You send a prompt, the agent picks tools, and you get results—but understanding why it chose one tool over another, or why it skipped a seemingly relevant option, is often opaque. That lack of transparency becomes a problem when you're debugging failures, auditing decisions, or trying to optimize your agent's behavior in production.

Embabel aims to address this by exposing the reasoning layer. The framework is designed to work with large language models and provides hooks that let you inspect the agent's decision-making process as it selects and invokes tools. The Baeldung article walks through practical implementation details: setting up the framework, defining tools, and configuring the observability hooks that surface reasoning traces.

While the article is light on full code samples in this feed snippet, the focus is clearly on developers who want more control and insight than typical high-level agent libraries provide. If you're working in Java and need to understand not just what your agent does, but why, this framework offers a structured approach. It's especially relevant if you're building systems where decision auditability matters—think compliance-heavy environments, regulated industries, or any scenario where "the AI did it" isn't an acceptable explanation. Embabel isn't the only observability-focused agent framework out there, but it's one of the few built specifically for the Java ecosystem, making it a natural fit if Spring Boot or other JVM tools are already part of your stack.

*Source: [Baeldung](https://feeds.feedblitz.com/~/960158825/0/baeldung)*
