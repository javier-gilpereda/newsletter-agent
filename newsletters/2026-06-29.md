## In Depth

### I used Claude Code to get a second opinion on my MRI

A developer with shoulder pain received an MRI diagnosis of a Grade III partial-thickness rotator cuff tear and immediately underwent aggressive treatment including shockwave therapy and homeopathic injections. Skeptical, he turned to Claude Code Opus 4.8 to analyze his 266MB DICOM MRI files. After an hour of automated analysis, Claude reported the tendon was intact—a dramatically different conclusion from the orthopedist.

The discrepancy prompted a second round of analysis where Claude used multiple subagents to arbitrate between the human and AI readings. After reviewing clinical movement tests and examining the images from multiple angles, Claude's verdict favored its own initial assessment: mild tendinosis with no discrete tear. This contradicted not just the grade of injury but the existence of a tear entirely.

What makes this compelling isn't whether Claude was right—medical imaging remains complex and this shouldn't replace professional diagnosis—but what it demonstrates about Claude Code's capabilities. Running in an agentic mode with code execution, package installation, and extended context, it could autonomously plan a sophisticated analytical workflow, install DICOM processing libraries, and reason across hundreds of image slices. The developer also caught that his treatment included therapies flagged as inappropriate by clinical guidelines, which ChatGPT helped identify.

This is a glimpse of AI as a research partner for informed patients, not a doctor replacement. The technology clearly has limitations—and the stakes in medical contexts are high—but the ability to get a detailed, reasoned second perspective on complex data in an hour is genuinely remarkable. It's also a reminder of the gap between chat interfaces and agentic tools: Claude Code's ability to execute extended workflows made this analysis possible in ways a simple chatbot couldn't match.

### GLM 5.2 beats Claude in our benchmarks

Semgrep just dropped surprising benchmark results: GLM 5.2, an open-weight model from China's Zhipu AI, outperformed Claude Code Opus 4.8 in detecting IDOR (Insecure Direct Object Reference) vulnerabilities. GLM scored 39% F1 versus Claude's 32%, at roughly $0.17 per vulnerability found. Both trailed Semgrep's purpose-built multimodal pipeline (53-61% F1), but that system uses extensive scaffolding—endpoint enumeration, guided navigation, and custom harnesses that do heavy lifting.

GLM 5.2 achieved this with just a prompt. No special tooling, no endpoint discovery, just the same basic IDOR detection instructions given to every model. The architecture is compelling: a Mixture-of-Experts design with 750B total parameters but only 40B active per token, keeping inference costs manageable. It extends context from 200K to 1M tokens and reportedly maintains reasoning quality across long agent trajectories—critical for security tasks that span multiple files and authorization frameworks.

The model was released under an MIT license on June 16, making it commercially usable and inspectable. On standard coding benchmarks, it posts the strongest open-weight numbers available. For security teams working in sensitive environments where running models on-premises matters, this is significant. It's also a milestone in the broader trajectory: open-weight models aren't just catching up to frontier models, they're now beating them in specific domains.

Semgrep's broader point is worth noting: they were trying to measure how much performance comes from the model versus the harness around it. The answer appears to be that scaffolding still matters enormously—their custom pipeline more than doubles GLM's performance—but the baseline capability of these open models is climbing fast. For developers integrating AI into security workflows, the competitive landscape just got more interesting.

*Source: [Hacker News Front Page](https://semgrep.dev/blog/2026/we-have-mythos-at-home-glm-52-beats-claude-in-our-cyber-benchmarks/)*

### Amazon Q flaw let booby-trapped Git repos execute code, swipe cloud creds

Wiz Research disclosed CVE-2026-12957, a high-severity vulnerability in Amazon Q for Visual Studio Code that allowed malicious Git repositories to execute arbitrary commands and steal AWS credentials. The flaw, assigned a CVSS score of 8.5, centered on how Amazon Q automatically loaded Model Context Protocol (MCP) server configurations from .amazonq/mcp.json files without user consent or workspace trust checks.

MCP is designed to let AI assistants launch local processes to carry out tasks—compiling code, running tests, querying APIs. The security model assumes users explicitly configure these servers, since they grant the AI permission to execute commands with access to your environment. Amazon Q violated that assumption by silently loading MCP configs from any opened repository. Those processes inherited the developer's full environment: AWS credentials, API keys, SSH sockets, authentication tokens. Opening a malicious repo and activating Amazon Q was enough to trigger execution.

Wiz demonstrated the attack with a proof-of-concept repository containing a weaponized MCP configuration. Simply opening the project folder caused Amazon Q to execute AWS commands using the victim's existing credentials. Amazon patched the issue in language server version 1.65.0, which should auto-update unless you've disabled that feature.

The broader warning from Wiz is that this isn't just an Amazon problem—it's an industry pattern. AI coding assistants increasingly adopt MCP to connect models to local tools, creating new attack surfaces in the hidden configuration files developers rarely scrutinize. As these tools gain more autonomy and integration with local environments, the security model needs to catch up. For now, treat repository configurations like executable code, because that's increasingly what they are.

*Source: [The Register](https://www.theregister.com/cyber-crime/2026/06/26/amazon-q-flaw-let-booby-trapped-git-repos-execute-code-swipe-cloud-creds/5263202)*

### Self-Correcting Structured Output in Spring AI 2.0

Spring AI 2.0 introduces self-correcting structured output, addressing a core challenge: LLMs produce text, but applications need typed objects. When models fail to generate valid JSON matching your schema, Spring AI now automatically detects the error, sends the malformed output back to the model with the schema and validation failure, and lets it retry. This correction loop runs transparently, turning unreliable text generation into reliable structured data without manual error handling in your code—bridging the gap between natural language interfaces and strongly-typed application logic.

*[Spring Blog](https://spring.io/blog/2026/06/23/spring-ai-self-correcting-structured-output)*

### A Guide to Agent Skills in Spring AI

Spring AI now lets you define lightweight Agent Skills—locally-packaged capabilities you can grant to AI agents for simple tasks where full Model Context Protocol (MCP) servers would be overkill. Think of Skills as functions your agent can invoke: reading files, calling APIs, or querying databases. They're defined in your application code and registered with the agent, giving you fine-grained control over what the agent can do without the overhead of external process communication that MCP requires for more complex integrations.

### Regular Expression Support in HQL

Hibernate Query Language (HQL) now supports querying string columns against regular expressions, letting you write pattern-matching queries directly in HQL rather than loading data into memory for regex filtering in Java. This is particularly useful for complex string matching in database queries—email validation, format checks, or extracting structured substrings—while keeping the logic declarative and database-backed. The tutorial covers syntax, performance considerations, and when regex queries make sense versus alternative approaches like LIKE patterns or full-text search.

### AI Tools Accelerates Coding, but Not Overall Software Delivery, GitLab Research Finds

GitLab's 2026 AI Accountability Report identifies an "AI Paradox": 78% of developers say they code faster with AI tools, yet overall software delivery hasn't accelerated. The bottleneck has shifted downstream—testing, code review, security scanning, and governance processes can't keep pace with AI-generated code volume. Organizations are producing more code but not necessarily shipping faster, and new challenges around traceability, quality assurance, and accountability are emerging. The finding suggests that optimizing individual coding speed without rethinking the entire delivery pipeline may just move the constraint rather than eliminate it.

*[InfoQ](https://www.infoq.com/news/2026/06/ai-coding-outpaces-governance/?utm_campaign=infoq_content&utm_source=infoq&utm_medium=feed&utm_term=global)*
