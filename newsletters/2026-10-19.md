## In Depth

### Safeguarding LLM Output in Spring AI

Spring AI is maturing fast, and one critical production pattern is now front and center: inspecting model output before it reaches your users. Baeldung's latest tutorial walks through building a custom advisor that intercepts responses from Spring AI's ChatClient, giving you a chance to validate, sanitize, or reject what the model generates.

This matters because LLMs can hallucinate, leak sensitive data, or return malformed output that breaks downstream logic. A custom advisor sits in the pipeline between the model and your application code, acting as a quality gate. You can check for profanity, verify structured output matches expected schemas, or enforce business rules—like ensuring a generated SQL query doesn't touch forbidden tables.

The tutorial shows how to implement this using Spring AI's advisor pattern, which integrates cleanly with the rest of your Spring Boot application. You register your advisor in the ChatClient builder, and it runs on every response. The code is straightforward: you get the model's raw output, apply your checks, and either pass it through or throw an exception.

What makes this especially useful is that it works with any Spring AI model provider—OpenAI, Azure OpenAI, or local models via Ollama. The advisor pattern is provider-agnostic, so you write the safety logic once and it applies everywhere. For teams already using Spring Boot, this is a much simpler path than standing up separate validation services or trying to bolt safety checks onto Python inference servers. If you're shipping LLM features in production, this pattern should be in your toolkit from day one.

### You Don't Need Python to Ship AI: Adding an LLM Feature to a Spring Boot API

The assumption that "adding AI" means spinning up a Python service is finally getting challenged. This detailed post demonstrates building a support ticket triage feature—category, priority, summary, tags—entirely within an existing Spring Boot API using Spring AI 2.0.1 and Java 21.

The goal isn't just to call a model; it's to handle the boring, critical parts that make it safe to deploy: typed output via Java records, request timeouts, token budgets to control costs, and fallback behavior when the model fails. The author tested against a local OpenAI-compatible mock server, forcing every failure mode—valid JSON, prose instead of JSON, hangs, 500 errors—to verify the code's resilience.

The architecture is clean. Spring AI's ChatClient uses a fluent API that feels like RestClient, making it familiar to Spring developers. You define what you want back as a Java record with enums for categories and priorities, and Spring AI deserializes the model's JSON into that structure. If deserialization fails, you catch it and return a fallback triage with source metadata indicating it came from a rule-based classifier, not the LLM.

Cost and latency controls are baked in from the start. The application.properties file caps max-tokens at 300 (triage answers are small), sets temperature to 0.0 for consistency, and configures a 6-second timeout with a concurrency limit of 8. These aren't afterthoughts—they're first-class configuration that keeps your AWS bill predictable. For Java and Kotlin shops already deploying Spring Boot services, this is a pragmatic blueprint: add AI as another feature in your existing stack, monitor it with the same tools, and skip the operational overhead of a polyglot architecture.

### Building Agents That Don't Break — Error Handling and Patterns in Spring AI

Agents that work in demos break in production for predictable reasons: tools time out, the model passes malformed arguments, queries return no results, or the agent loops without progress. This article tackles those failure modes head-on with patterns for planning, recovery, and preventing runaway behavior in Spring AI agents.

The core principle: tools should never throw exceptions. When a tool fails, the agent loop breaks and the model never sees what went wrong. Instead, catch every exception inside the tool and return it as a readable string. The model then gets context—"Weather service is temporarily unavailable"—and can respond intelligently: suggest alternatives, skip that part of the answer, or tell the user the service is down. This turns brittle failures into graceful degradation.

Validation matters just as much. The model constructs tool arguments from natural language, and edge cases slip through—wrong formats, unsupported values, empty strings. Validate every argument at the tool entry point and return descriptive errors. If a date arrives as "Nov 15" instead of "2026-11-15," return "Error: date must be in YYYY-MM-DD format. Received: Nov 15." The model sees its mistake and can retry correctly.

For complex tasks, prompt the model to plan before acting. A simple instruction—"outline the steps you will take, then execute them"—improves output quality significantly. The model breaks multi-city trip planning into discrete steps (get weather, find hotels, check ticket prices), and each step is easier to verify and debug. Combined with partial result handling (return what you have even if one tool fails) and structured output validation, these patterns turn fragile prototypes into agents you can actually deploy. If you're building with Spring AI, this is required reading.

### From Microservices to Agents: The Next Evolution of Distributed Systems

Distributed systems are shifting from microservices to agentic AI architectures, and the change is more than cosmetic. Microservices decompose systems by function—each service owns a bounded capability. Agentic systems decompose by decision-making authority—each agent reasons, acts, and adapts autonomously. This introduces new complexities in observability (how do you trace decisions that emerge from model inference?), reliability (agents can fail in non-deterministic ways), and system design (coordination between agents isn't just API contracts anymore). The article argues that existing architectural patterns need updates to accommodate agents as first-class citizens in distributed systems, not just bolted-on features.

### Reverse Engineer Anything Project Brings AI Agents to Binary Analysis

### Going All In On JVM 25 Virtual Threads

The AngularAndSpring project has been refactored from Spring Reactor to Spring blocking APIs using JDK 25 and virtual threads. The original architecture used Reactor's limited thread pool to avoid sleeping OS threads, maximizing efficiency under load. Virtual threads change the calculus: they're cheap enough that you can spawn millions without worrying about thread-pool exhaustion. The refactor replaces reactive pipelines with straightforward blocking calls, trading Reactor's complexity for simplicity while maintaining scalability. For teams considering the leap from reactive to virtual threads, this real-world migration offers a concrete before-and-after comparison of architecture, code clarity, and performance under load.

*[DZone Java](https://dzone.com/articles/jvm-25-virtual-threads)*

### Tmux and Claude Code: Sessions, Send-Keys, and the Ceiling

As AI agents like Claude Code gain the ability to execute shell commands, developers are realizing that tmux—the terminal multiplexer—is a surprisingly powerful interface.
