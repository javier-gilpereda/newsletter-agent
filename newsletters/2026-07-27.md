## In Depth

### Introducing Claude Opus 5

Anthropic just released Claude Opus 5, and the early buzz suggests it's a significant step forward. Positioned as a "thoughtful and proactive model" that approaches Fable 5's frontier intelligence at half the price, Opus 5 currently leads the Artificial Analysis leaderboard—even ahead of Fable 5 itself. It's priced identically to Opus 4.8 and continues to offer a "fast mode" at 2× cost.

The standout feature? Relentless autonomy. In one benchmark task, Opus 5 was given a drawing of a machine part and asked to generate FreeCAD code to rebuild it—but deliberately given no way to view the drawing directly. The model responded by writing its own computer vision pipeline to extract geometry from raw pixels, then reconstructed the entire part. That level of self-directed problem-solving is a clear shift from models that wait for explicit instructions.

Security considerations remain front and center. Anthropic intentionally avoided training Opus 5 on cyber exploitation tasks, though the model improved substantially at finding vulnerabilities as a byproduct of general capability gains. Crucially, it still lags far behind Mythos 5 on actually exploiting those vulnerabilities—a deliberate design choice to reduce dual-use risk. Anthropic has published both a dedicated prompting guide and new context engineering rules for the Claude 5 generation, reflecting how much prompt best practices have evolved. The takeaway: if you're still stuffing examples into system prompts or littering them with "don't do X" instructions, you're likely degrading performance on these newer models.

### A Fireside Chat with Cat and Thariq from the Claude Code team

Simon Willison sat down with Cat Wu and Thariq Shihipar from Anthropic's Claude Code team at the AI Engineer World's Fair, and the conversation offers rare insight into how the team actually uses their own product. One headline stat: Claude Tag—Anthropic's collaborative Slack integration—now lands 65% of product engineering PRs for the Claude Code team itself. That's not a demo metric; it's their daily workflow.

The team's development philosophy is grounded in aggressive internal dogfooding (which they call "ant fooding"). Claude Code ships features to Anthropic employees first, and only features that demonstrate retention with that internal cohort make it to external release. Critical changes still get manual code review, but the team increasingly relies on automated review for outer-layer work. The shift in day-to-day work is stark: Cat describes moving from micromanaging every permission prompt in early Sonnet 3.7 days to delegating entire features in one shot with Fable. Thariq's focus has shifted to ensuring output quality meets the team's exacting brand standards—in hours, not days.

Prompt engineering wisdom has inverted. Adding examples to system prompts is no longer best practice for Fable 5 or even Opus 4.8. The Claude Code system prompt recently shrank by 80%, and lists of prohibitions ("don't do X, don't do Y") now actively degrade performance. The team believes deeply in auto mode as an enabling technology, particularly for Claude Tag's collaborative workflows. Thariq's advice for avoiding "Deep Blue" (the existential dread of agents doing your job) is simple: be more ambitious with the work you take on. Fable is competent enough to edit video—Thariq used it to edit its own launch video.

### Stop Burning Claude Tokens: Propagate SSE Disconnects in Spring Boot

Here's a problem that's costing real money: a user closes their browser tab mid-stream while receiving a Claude response, but your Spring Boot backend keeps streaming from Anthropic in the background, burning tokens to render output for a dead TCP socket. The root cause? Most developers assume reactive magic "just works"—that wrapping an API call in a Flux<String> will automagically abort the underlying HTTP/2 request when the client drops the SSE connection. It won't.

The issue is lifecycle binding. Spring's SseEmitter doesn't trigger thread interrupts upstream unless explicitly instructed to handle socket hangups. Virtual threads unblock I/O gracefully, but that doesn't help if the reactive subscription isn't canceled. Setting standard socket timeouts won't kill an active stream—as long as Claude keeps generating tokens, your backend thinks everything is healthy. You're literally paying for invisible tokens.

The fix is straightforward but non-obvious: bind your client transport lifecycle directly to the upstream Anthropic streaming request. Register lifecycle hooks on SseEmitter.onCompletion() and SseEmitter.onTimeout(), and use them to trigger abort signals on the WebClient subscription's Disposable handle. This ensures the upstream Claude API call cancels instantly when the client disconnects. Configure Spring AI's ChatClient with a custom transport layer that honors subscriber teardown, and track zombie stream counts in Micrometer to audit daily token savings. The author built this pattern while prepping for senior roles at javalld.com, and the code sample shows exactly how to wire the dispose call into emitter callbacks. Bottom line: unbounded LLM streams without explicit teardown triggers are a cloud bill explosion waiting to happen.
