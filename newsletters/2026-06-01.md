### Embedding HTML UIs in MCP Servers With Spring AI

Spring AI just unlocked a fascinating capability: embedding interactive HTML user interfaces directly inside Claude Desktop chat conversations. This Baeldung tutorial walks through building a Model Context Protocol (MCP) server using Spring AI, connecting it to Claude Desktop, and serving rich UI components that users can interact with without leaving the chat window.

The approach leverages Spring Boot's familiar programming model while integrating with Anthropic's MCP specification. Developers can create tools that don't just return text—they return complete HTML interfaces with forms, buttons, and dynamic content. The server handles tool calls from Claude, processes requests using Spring's ecosystem, and renders responses as embeddable UI components.

This matters because it fundamentally changes how AI assistants can present information and collect input. Instead of asking users to copy-paste data or navigate to external tools, you can build inline calculators, data visualizers, configuration panels, or approval workflows. For enterprise applications, this could streamline everything from approval processes to data entry tasks, keeping users in a single conversational flow while giving them structured, interactive controls when needed. It's a practical bridge between the flexibility of natural language and the precision of traditional UIs, built on Spring's mature infrastructure.

### Guide to Subagent Orchestration in Spring AI

Building complex AI systems often requires coordinating multiple specialized agents, each handling a specific domain or task. This new Baeldung guide tackles subagent orchestration using Spring AI and the Spring AI Community Agent Utils library, showing how to architect systems where a coordinator agent delegates work to specialized subagents.

The pattern addresses a common challenge: single agents struggle with broad domains, but manually routing between multiple agents creates brittle code. Subagent orchestration provides a middle ground. A primary agent analyzes incoming requests, determines which specialized agent (or agents) should handle each part, delegates accordingly, and synthesizes the results. Spring AI's tools and function-calling capabilities make this coordination surprisingly clean, while the Agent Utils library provides abstractions for common patterns like result aggregation and error handling.

This architecture matters for production systems that need both breadth and depth. Imagine a customer service system where one subagent handles account lookups, another processes refunds, and a third manages technical troubleshooting—each optimized and tested independently. The orchestrator handles the conversational flow and delegates to specialists. It's more maintainable than a monolithic prompt, more flexible than hard-coded routing, and scales better as you add capabilities. For Java and Spring Boot teams building AI features, this is a practical pattern that fits naturally into existing service-oriented architectures.

*Source: [Baeldung](https://feeds.feedblitz.com/~/957590267/0/baeldung~Guide-to-Subagent-Orchestration-in-Spring-AI)*

### Koog 1.0 Is Out: Stable Core, Better Interop, and Multiplatform Observability

JetBrains announced Koog 1.0 at KotlinConf 2026, marking the framework's transition from experimental to production-ready. Koog is an open-source framework for building AI agents in Kotlin and Java, providing tools, workflows, persistence, memory, observability, and integrations for both JVM and Kotlin Multiplatform projects.

The 1.0 release brings a critical stability guarantee: no breaking changes in stable modules for at least one year. For teams building production agents, this commitment matters—it means you can build on Koog without worrying about constant API churn. The release also includes practical improvements: local Android AI support with LiteRT models, a redesigned Java interop layer that feels more natural for Java developers, decoupled HTTP transport for easier integration with existing infrastructure, and OpenTelemetry support across all targets including multiplatform environments.

Additional features include improved persistence and memory for long-running agents, and Anthropic prompt caching support to reduce both latency and token costs for repeated prompts. The framework is structured with stable core modules and beta modules for evolving functionality, letting teams adopt proven patterns while experimenting with newer features. For JVM and Kotlin developers building agentic applications—whether internal tools, customer-facing assistants, or automation systems—Koog 1.0 provides a solid foundation backed by JetBrains' engineering and a year's worth of community feedback.

*Source: [JetBrains Kotlin](https://blog.jetbrains.com/ai/2026/05/koog-1-0-is-out-stable-core-better-interop-and-multiplatform-observability/)*

### Rethinking Java CRUDs With Event Sourcing and CQRS Patterns

Traditional CRUD systems overwrite state, losing history with every update. Event Sourcing inverts this: instead of storing current state, systems persist the event sequence that caused each state transition, deriving current state by replaying history. Combined with CQRS—separating write models from read models—this architecture enables audit trails, time-travel debugging, and optimized query patterns. This DZone article explores why these patterns matter for Java systems, when the complexity is justified, and how to implement them effectively without over-engineering simpler domains.

*[DZone Java](https://dzone.com/articles/java-crud-event-sourcing-cqrs)*

### Lombok vs Java Records: When to Use Which in 2026

Java Records arrived as a first-class language feature, but Lombok still has its place. This guide from a backend engineer working with Java 17 and Spring Boot breaks down when each tool makes sense based on production experience. Records excel for immutable DTOs with minimal ceremony, while Lombok shines for complex builders, mutable entities, and cases needing fine-grained control over generated code. The article cuts through the either-or debate with practical criteria: use Records by default for simple immutable data, reach for Lombok when you need flexibility or legacy compatibility.

*[Dev.to Java](https://dev.to/shubham_bhati/lombok-vs-java-records-when-to-use-which-in-2026-18c3)*
